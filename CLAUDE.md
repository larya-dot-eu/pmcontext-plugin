# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What This Is

A Claude Code plugin — no application code. It ships seven slash commands (`/pmcontext:*`) as Markdown instruction files. When a user invokes a command, Claude reads the `.md` file and follows the instructions directly.

## Plugin Structure

```
.claude-plugin/plugin.json      — plugin metadata (name, version, author)
commands/pmcontext/             — one .md file per slash command
  init.md                       — one-time Supabase setup + table creation + PLUGIN_DIR discovery
  start.md                      — session orientation, scaffolds missing files, loads project context
  plan.md                       — 5-phase PM-Claude planning workflow, produces a plan file
  execute.md                    — runs a plan file end-to-end with TDD + task tracking
  resume.md                     — continues the last paused/active session
  close.md                      — writes session receipt to Supabase, updates pm_state
  status.md                     — quick dashboard (decisions, risks, active session)
templates/                      — files scaffolded to user projects on first /pmcontext:start
  CLAUDE.md.example             — pmcontext workflow block appended to project's CLAUDE.md by init + start
  CONTEXT.md                    — PM-Claude protocol (Node Model, communication tags, roles)
  PROJECT_BRIEF.md              — generated by the codebase tour, not a static template
  ROADMAP.md                    — minimal ROADMAP starter, always filled via brainstorming
  PLANNING.md                   — the PM-Claude planning workflow (single source of truth for plan.md)
```

## How Commands Work

Each command file is plain Markdown. The frontmatter `description:` field appears in `/help`. The body is a series of steps Claude executes literally — reading files, running Bash, calling Supabase MCP tools, querying SQL.

**All commands share the same bootstrap pattern:**
1. Read `~/.pmcontext` to get `SUPABASE_PROJECT_ID` and `PLUGIN_DIR`
2. Derive the project name from `git rev-parse --show-toplevel | basename`
3. Use both values in every Supabase MCP call

`PLUGIN_DIR` is the path to the plugin installation, written by `init.md` at setup time. Commands that scaffold files (e.g. `start.md`) read templates from `$PLUGIN_DIR/templates/`.

## Supabase Schema

Two tables, created by `/pmcontext:init`:

- **`pm_sessions`** — one row per plan execution. Tracks `project`, `plan_path`, `status` (`active`/`paused`/`completed`), `current_step`/`total_steps`, and a receipt of `files_changed`, `commands_run`, `risky_assumptions`, `manual_checks`, etc.
- **`pm_state`** — one row per project (keyed by git repo name). Stores `open_decisions` (JSONB array), `active_risks` (JSONB array), and `last_checkpoint`.

Both use `CREATE TABLE IF NOT EXISTS` — safe to re-run.

## External Dependencies

Commands require these to be configured in Claude Code before use:

- **Supabase MCP** — required by all commands except during editing this repo
- **`superpowers` skills** — `executing-plans`, `test-driven-development`, `writing-plans`, `brainstorming`, `requesting-code-review`, `verification-before-completion`, `using-git-worktrees`, `finishing-a-development-branch`
- **context7 MCP** — required by `execute` and `resume` when the plan's `Libraries touched` field is non-empty

## Planning Workflow

The PM-Claude planning workflow (5 phases: context priming → exploration → spec writing → plan writing → adversarial review) is defined in **`templates/PLANNING.md`** — this is the single source of truth. Do not duplicate its content elsewhere.

`commands/pmcontext/plan.md` orchestrates the workflow by reading `$PLUGIN_DIR/templates/PLANNING.md` at runtime and following its phases. If the planning workflow needs updating, edit `templates/PLANNING.md` only.

## Plan File Convention

Plans are created by `/pmcontext:plan` and saved to `docs/superpowers/plans/` (gitignored). Plans executed by `/pmcontext:execute` must end with a `## Session Launch` section:

```markdown
## Session Launch

What this builds:
Codebase state going in:
Files the plan touches:
Libraries touched:
Key design decisions:
Gotchas:
Start here:
End here:
```

The `Libraries touched` field controls whether context7 MCP is required.

## Communication Protocol

When working in any project that uses this plugin, all messages should use the tags defined in `CONTEXT.md`: `[SURFACE]`, `[CORE]`, `[VERIFY]`, `[CHECKPOINT]`, `[RISK]`, `[BLAST RADIUS]`, `[REFACTOR]`, `[STEELMAN]`. These tell the PM (human) how to respond without reading code.
